| D-021 | 2026-09-02 | `HoloMaterial` is modelled on the foil trading card in the Doodlemon puzzle view (a photographed holo card with a gentle float), not on the landing-page tiles (which only lift on hover). Bloomlab reproduces the foil optics in CSS — sweeping spectral bands, metallic grain, pointer-following glare, rim light, direction-aware shadow — and adds the pointer physics the spec asks for (≤ 6° tilt, 420 ms settle, touch press/drag/release). | D-022 | 2026-09-02 | HoloMaterial smoothing (follow and settle) is exponential easing in a `requestAnimationFrame` loop that writes seven custom properties and stops when the pose converges; the stylesheet has no transitions on the pointer-driven properties. | In the production bundle, CSS transitions on properties whose values come from `var()`-driven `calc()` never advanced (transform, band position, glare and shadow all stayed at their pre-hover values on the deployed preview while `transition: none` fixed them instantly); the dev server did not reproduce it. Easing in JS behaves identically in dev, in production and in tests, gives a spring-like feel, and costs a few multiplications per frame only while a card is moving. |
| D-023 | 2026-09-02 | From a live study of the reference (real pointer): its tiles lift 8 px with a deeper shadow and a pastel gradient ring on hover, its foil card is a photograph with a slow float, and the only pointer-driven motion is a background parallax. Bloomlab adopts the *tactile* half — the hover lift is 5 px and the shadow deepens with it, and the rim light is tinted with the palette so the edge reads as iridescent foil — and keeps its own procedural material and spec physics (tilt, glare, spectral shift, settle). No idle float, no parallax, no copied gradient values. | Spec §62 asks to match the reference's tactile, holographic *feeling* and forbids copying art or composition; §148 / MOT-004 forbid constant animation. The lift-and-shadow cue is what makes the reference's hover feel physical; the tinted rim answers "iridescence" without a photograph. |
| D-024 | 2026-09-02 | Visual acceptance reviews run through a small DevTools-Protocol driver (`scripts/review/`, `npm run review:capture` / `review:holo`) against a production build, with outputs in the git-ignored `.review/`; the in-app browser pane is used for spot checks only. | The pane only composites frames during input actions, cannot emulate reduced motion, and its captures time out or tile at fresh navigations, so eased motion looked broken and narrow widths could not be captured reliably. | D-030 | 2026-09-02 | Revision semantics: the server assigns `revision` when it accepts a write (1 on insert, +1 per accepted change); a client adopts the server number at each sync point and bumps it locally between syncs; a push carries `base_revision` (the last server revision the client saw, kept in `sync_shadow`). Merge kinds per entity live in `@bloomlab/shared` (`SYNC_ENTITY_KINDS`): `simple` = fast-forward else newest `updated_at` wins; `append` = id-addressed union; `snapshot` = divergence from another device is a conflict for the learner to resolve (`force` applies the choice). `notes` is a snapshot entity. | Spec §91 / TA§14 name the three rules but not how to detect divergence; a base revision is the smallest thing that does. Notes carry prose, so silently dropping one side would be exactly the destructive merge §146 forbids. |
| D-031 | 2026-09-02 | The device keeps its canonical sync key in IndexedDB (`device.sync_key`) so the learner can show, copy or re-download it; requests carry only the per-device session token (`device.session_token`). | D-043 | 2026-09-02 | Learner evidence is append-only; skill progress, campaign progress and the review queue are *derived* rows recomputed from evidence on every device (and after every sync that pulled something), never authored. Derived ids are learner-scoped and deterministic (`sp:<skill>:<hash of learner id>`), so two devices write the same row and two learners never collide on D1's id key; provisional rows are dropped when a device links. | Evidence is the record of truth (spec §30); derivation keeps every device convergent without merge logic, and a rule change only needs a recompute, not a migration. |
| D-044 | 2026-09-02 | The mastery ladder is earned from kinds of evidence and assistance, never from a score threshold: LEARNING on any evidence, GUIDED on a pass with any help, PRACTICED on a pass with at most light help, INDEPENDENT on an unassisted pass, PRESSURE_TESTED on an unassisted pressure pass, MASTERED on the skill's declared count of unassisted passes (never fewer than two, over two distinct demonstrations) plus every declared requirement. All constants live in `packages/mastery-engine/src/rules.ts` under `MASTERY_RULES_VERSION`, and every stored evaluation records that version. | Spec §29–§34 ask for evidence-based, inspectable, testable rules; a versioned rules module makes a rule change a visible diff and keeps old evaluations attributable. |
| D-045 | 2026-09-02 | Assistance rolls up from hint use by a fixed table: worked example → heavy; concept reminder or three nudges → guided; one or two nudges → light; nothing → independent. A guided-practice exercise (or one authored in `guided` mode) is guided at least. Only `independent` passes of independent-capable kinds count toward INDEPENDENT and MASTERED; light-assisted passes count toward PRACTICED. | Spec §28 and §34 (a heavily assisted pass is not independent evidence; mastery requires sufficient independent evidence) made explicit and testable (MAS-011). |
| D-046 | 2026-09-02 | NEEDS_REFRESH is an overlay, not a demotion: the earned ladder state stays in the record as `refresh_from`, and a passed retrieval restores it because evaluation is a pure function of the evidence history. A skill needs refresh when its review is overdue by more than 14 days or its latest attempt is a failed retrieval, and only a retrieval passed with at most light assistance clears it; review intervals are 10 / 21 / 35 / 60 days by earned state, divided by importance and shortened by the recent failure rate, never below 3 days. | Spec §32 and TA§69: old skills resurface, review never blocks, and historical mastery evidence is never erased. |
| D-047 | 2026-09-02 | Prerequisite satisfaction and gate availability read only the earned ladder state (INDEPENDENT or above), never the clock: a refresh-due prerequisite still unlocks what depends on it, and any skill whose prerequisites are satisfied is available wherever it sits in the campaign (`work_ahead`). Placement gates are `optional` and never the current gate. | Spec §7 and §143 (fully asynchronous, no calendar locks, work ahead when competency is shown). |
| D-048 | 2026-09-02 | The session builder is a fixed order of decisions with budget shares: due retrieval first (≤ 20 % of the budget, never blocking), then repair (weak prerequisites of the next work, recent failures, and assisted passes when assistance dependence ≥ 0.5), then the learner's focus, then the current gate's required skills and available work-ahead skills, then pending fieldwork and the active project. Each item carries its reason; "Continue" rebuilds with the finished items excluded. | Spec §33 and TA§70: algorithmic, deterministic, no AI, always continuable. |
| D-049 | 2026-09-02 | Every attempt and evidence record stores the version stamp `{app, content, content_hash, simulator, rules}` at write time and is never rewritten; recompute may change derived rows (which record the content version they were computed under) but never evidence. Phase 6 adds the `exercise_attempts` record as the parent of evidence rows so INF-013 / CNT-007 / DATA-011 are provable now rather than in Phase 9. | Spec §30 and §101; TA§82 (content update safety). |
| D-050 | 2026-09-02 | `last_demonstrated` (the anchor of every review interval) is the latest pass at the PRACTICED bar or better — an independent-capable kind with at most light assistance. A guided or worked-example pass neither restores a NEEDS_REFRESH skill nor postpones its review. Rules bumped to `2026.09.02-r2`. | Found by the explicit refresh round-trip test before merge: with any pass counting, a worked-example retrieval cleared NEEDS_REFRESH and reset the review clock, contradicting MAS-011. |
| D-051 | 2026-09-02 | What resets the review clock is an explicit rule, `DEMONSTRATION_RULES` / `isDemonstration`: a `passed` attempt of a demonstration kind (deterministic or independent exercise, pressure test, explanation, sales use, fieldwork or real-GHL proof — only with the proof provided — and retrieval) with no critical failure and at most light assistance. Exposure, quizzes, guided practice, failed or partial results and guided or heavy assistance never move it. Unverified fieldwork (no proof provided) is not a pass anywhere in the engine. Rules bumped to `2026.09.02-r3`. | The user asked for the rule to be explicit rather than incidental; making fieldwork proof part of `isPass` keeps the ladder, counts and review clock consistent with spec §30 "real-GHL evidence where required". |
| D-052 | 2026-09-03 | Retrieval is a review demonstration, not a progression kind: `INDEPENDENT_KINDS` (deterministic and independent exercises, pressure tests, explanation, sales use, fieldwork, real-GHL) drive INDEPENDENT and MASTERED; `REVIEW_DEMONSTRATION_KINDS` (those plus retrieval) drive `last_demonstrated` and the NEEDS_REFRESH overlay. A passed retrieval restores an earned state and advances `review_due` but never adds an independent demonstration. Rules bumped to `2026.09.03-r4`. | Spec §32 describes retrieval as short challenges that keep old skills alive; letting a five-minute retrieval count as the second demonstration toward MASTERED over-credited it. |

What changes is the run's header (`sim_projects`, a `snapshot` entity, one row per run, patched and never recreated, so no second run appears in the list), which names the generation that is current; a load reads that generation and takes only the rows carrying it, leaving the earlier lives inert rather than erased. Membership is decided by the `run_id` and `generation` fields rather than by parsing an id, and a row saved before generations existed carries none and reads as generation `0`, so a run the earlier build stored still loads and still resumes. Whether an event still needs writing is decided by its sequence within the current generation, never by a primary key from another one. | The requirement was that a reset produce the authored initial state *and* a usable run, and it produced only the first. Every alternative broke something the architecture guarantees: hard deletion destroys facts other devices hold, overwriting mutates an append row, and minting a whole new run id would put two runs of one scenario in the learner's list and orphan every reference to the old one. A generation is the smallest identity that keeps the run one run, the history immutable, and the two lives apart. |
