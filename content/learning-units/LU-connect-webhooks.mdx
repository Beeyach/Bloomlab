# Accept an event once when it arrives twice

## Trust precedes effects

Outbound webhooks send notifications; inbound webhooks receive them. Map the minimum fields needed, keeping event ID separate from contact ID. One contact can generate many legitimate events.

The current HighLevel Marketplace guide prefers X-GHL-Signature with Ed25519 verification, retaining X-WH-Signature as the legacy RSA transition path. A header's presence is not verification. Use the current provider key and documented signed-message contract; reject failed verification. Marketplace events are not the same feature as a workflow's Custom Webhook or Inbound Webhook trigger.

## Repeated delivery is normal

HighLevel documents retries for non-2xx and missing responses, with backoff and jitter. Do not assume exactly-once delivery. A stable event ID should be scoped to sender/account and claimed with an atomic durable receipt/effect strategy. An in-memory set vanishes on restart. Marking handled before durable work can lose an event; applying effects before claiming can duplicate it.

A committed duplicate should acknowledge without another effect. A new event for the same contact is not necessarily duplicate. Preserve redacted identifiers and failure reasons. Before replaying, fix the cause and reconcile what already committed.

## Training boundary

The fixture supplies signature-valid and already-processed facts; Bloomlab does not perform cryptographic verification here. Apply authenticate, validate, identify, safely commit and acknowledge in that order. Invalid authentication fails closed.

An integration needs an owner, monitoring, bounded retries and a recovery procedure. Prefer a native workflow when it solves the job. Marketplace extensions and custom app lifecycle are specialist work; no app, webhook or real account connection is created by this practice.
