# Debug permission without sharing a key

## Four distinct questions

A project groups resources, configuration and billing. A service account is a workload identity. A credential proves identity. An IAM role grants permissions on resources. Possessing a key does not permit access to every project; enabling an API does not grant the caller its permissions.

Name the resource project, actual caller, API and minimum permission. Prefer attached identity, impersonation or federation when supported instead of long-lived keys. A developer's local user identity may differ from the deployed workload's identity.

## Inspect the failing layer

Read the status and structured reason, project, API enablement and IAM policy. A 403 has several possible causes; do not respond by granting Owner. A missing documented read permission needs a narrowly reviewed role on the intended resource. A disabled API requires the authorised project administrator to evaluate enablement. Invalid or expired credentials are authentication problems.

Do not distribute credential files to troubleshoot. Redact private keys, tokens and personal data from logs and screenshots. If a key is exposed, removing it from a file is insufficient: revoke or rotate and investigate use. Do not claim old Git or artifact copies were removed.

## Transfer responsibility safely

Record project owner, workload identity, permitted operations, billing boundary and revocation procedure. Test synthetic inputs with restricted permissions. Keep any unavoidable credentials in authorised server-side secret storage, never browser variables or lesson answers.
