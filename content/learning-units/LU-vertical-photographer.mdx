# Photographer Inquiry System

## Demonstration Build — not a client outcome

This fictional photographer sells a date-sensitive service. The demonstration manifest contains an inquiry form with event date, event type and location; a pipeline with Availability Review, Proposal Sent and Confirmed; an owner notification; and a bounded proposal follow-up workflow. An inquiry records interest. It must not silently reserve the date.

Staff check availability and scope before sending a proposal. The source template has no universal package price or automatic availability promise. Use reusable values for brand and approved gallery link, but maintain client-specific packages as reviewed configuration. A form's requested date is not proof that the photographer is available.

Under this demonstration's contract, confirmation requires both a signed agreement and the required deposit recorded by the authorised owner. Proposal sent alone is insufficient. If either condition is unknown, keep the record under review. A refund or changed event date can invalidate the prior decision and requires deliberate human handling rather than a celebratory automated confirmation.

Follow-up stops on a reply, explicit decline or DND, and unresolved proposals have an owner and review date. This starter excludes image delivery, gallery hosting, editing, contract execution and payment processing. Those dependencies are recorded, not faked by a successful local fixture.

Measure inquiry-to-proposal and proposal-to-confirmed against consistent cohorts. Rehearse conflicting dates, a signed-but-unpaid agreement, duplicate inquiry and declined proposal. Preserve the difference between a prospect's request, a staff decision and a confirmed commercial commitment.

## Reuse with evidence

This is an explicit Bloomwired training blueprint. Repair its supplied manifest and trace the failure case below; the shared runner saves the answers and deterministic evidence. It does not import a HighLevel snapshot or execute outbound work. A local pass verifies only these supplied contracts. A real deployment still needs permission, destination-specific QA and honest proof. Never present this fictional system as a paid engagement, live result or customer testimonial.
