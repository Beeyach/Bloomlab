# Bloomwired Med Spa Core

## Demonstration Build — not a client outcome

The training source is a fictional med-spa consultation system, not a clinical record. Its manifest contains a consultation inquiry form, one consultation calendar, an inquiry pipeline, a booking follow-up workflow and an appointment reminder workflow. Use contact fields for treatment interest and custom values for the business name and booking destination. Do not add a custom object merely to store one scalar interest.

Capture permission and the preferred channel. A submitted inquiry creates or updates the contact and opens the agreed inquiry journey. A booked appointment stops inquiry nudges; appointment-specific reminders are a separate journey keyed to that booking. Cancellation stops obsolete reminders and routes to an explicitly permitted recovery path. A clinical eligibility question belongs with qualified staff, not an automated promise.

The template excludes diagnosis, treatment advice, outcome guarantees and medical-record storage. It also excludes paid acquisition and clinical intake. Its measurement contract compares inquiry-to-booking and booked-to-attended counts for the same cohort; a screenshot of a full diary is not attribution evidence.

Before a second-location rehearsal, replace the location name and booking destination, review staff/timezone, then test a duplicate inquiry, booking, cancellation and DND. Keep a change log showing exactly which assumptions differ.

## Reuse with evidence

This is an explicit Bloomwired training blueprint. Repair its supplied manifest and trace the failure case below; the shared runner saves the answers and deterministic evidence. It does not import a HighLevel snapshot or execute outbound work. A local pass verifies only these supplied contracts. A real deployment still needs permission, destination-specific QA and honest proof. Never present this fictional system as a paid engagement, live result or customer testimonial.
